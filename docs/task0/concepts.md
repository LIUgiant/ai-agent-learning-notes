# Agent 基础概念

## 1. 我如何理解 Agent 的三个组成部分

**`Agent = LLM + 上下文 + 工具` 是工程拆分，不是数学恒等式。** 模型根据输入选择下一步；上下文给出此刻可用的信息；工具把选择接到可观察、可改变的对象上。

以“汇总多币种报销”为例：

| 部分 | 具体内容 | 缺失后的问题 |
| --- | --- | --- |
| LLM | 理解报销要求，决定先换汇再求和 | 只有接口和数据，没有灵活的任务决策 |
| 上下文 | 原始金额、币种、工具说明、已返回的汇率与计算结果 | 可能忘记已完成的操作，或用猜测补齐事实 |
| 工具 | 读取报表、查询汇率、确定性计算 | 模型可以描述计算计划，但没有执行与取证手段 |
| 环境 | 文件内容、外部汇率服务、数据库中的报销记录 | 它在 Agent 外部；工具接口不等于工具背后的世界 |

上下文既包含观察，也包含指令、工具 schema 和历史。把它比喻成“眼睛”有助于入门，但上下文不等同于强化学习中的整个观察空间。工具 schema 是模型能看见的信息；实际执行工具的适配器是框架代码，二者职责不同。

## 2. Agent loop：让一次回答变成反馈循环

可以把一次执行记成以下顺序：

1. Harness 把任务、工具定义和已有轨迹组装为本轮上下文。
2. 模型返回答案，或者提出一个或多个工具调用。
3. 运行时检查工具名称、参数和权限，再调用工具。
4. 将工具调用与对应结果写回轨迹，保留调用 ID 的配对关系。
5. 下一轮模型根据新增观察决定继续、调整方案或结束。
6. 到达轮数/时间/成本上限、不可恢复错误或可靠验收结果时停止。

书中的 ReAct 表达为思考、行动、观察。公开轨迹足以记录动作与证据，并非每个模型都向客户端公开内部推理，也不能把“没看到 reasoning 文本”解释成“没有推理”。

本次网络搜索离线 demo 回放了两次 `thought → action → observation`，随后给出 `answer`。这是固定脚本示例，说明轨迹如何连接，不是在测模型是否会自主搜索。`context` 的工具练习则确实执行了计算、固定汇率换算和本地 PDF 解析，但工具调用顺序由学习脚本安排，也不是 LLM 自主决策。

一个关键的验收区别：`completed` 表示循环返回终止响应；`task_success` 才表示任务符合评分规则。即使算出的总数碰巧正确，如果所需汇率从未进入上下文，也不能称为“基于工具观测完成”。正确性与依据充分性应分开核查。

## 3. Harness 的边界和五项职责

同一个 Agent 可以从生产运行角度写成 `Agent = Model + Harness`。Harness 是 Agent 内部、模型外部的运行与管理层，不是“世界上除了模型以外的一切”。

| 职责 | 本次实践中的对应 |
| --- | --- |
| 上下文管理 | 区分全文历史、去历史、去 reasoning、隐藏工具结果等消融输入 |
| 工具接口 | 使用已有 `ToolRegistry` 的参数与结构化返回值 |
| 约束 | 只选离线路径；不继承密钥；禁止网络；限制测试运行时间 |
| 验证 | 数值断言、消息协议测试、证据 manifest 测试、锁文件检查 |
| 纠正 | 先定位失败原因，再调整学习脚本或隔离环境并复测；不把失败写成成功 |

`.venv`、运行脚本和工具适配代码是工程设施；被 PDF 工具读取的文件内容、游戏房间与背包状态是环境。即使 Q-learning 游戏和 Agent 都在同一 Python 进程里，也不改变这个概念边界。

## 4. 模型能力与工程能力分别解决什么

模型提供语义理解、判断、规划、工具选择和参数生成能力。工程层负责把正确的信息和能力接口交给它，并落实可执行的边界、保存状态、验证结果与恢复错误。工具调用策略能通过训练进入参数，但数据库操作、网络服务与沙箱执行机制仍在模型之外。

因此遇到失败时，我会先分辨：

- 模型没见到发票：先补充观察与上下文，不急于更换模型。
- 模型选对工具但参数字段错：改善 schema、校验与明确错误反馈。
- 工具超时：用有限重试、幂等机制和明确停止状态处理。
- 已有足够数据和合适工具，却反复作出错误判断：建立代表性评估后再考虑更强模型或后训练。
- 模型声称完成但没有交付物：以产物/结构化状态验收，不接受一句“完成了”。

工程机制能控制和检测一类错误，却不能凭空补出模型没有的知识与判断能力，也不能承诺零错误。更强模型可能吸收提示词改写、格式修复等适配代码的作用；此时应通过评估精简这些代码，而权限、业务数据完整性和结果验收仍需系统承担。

## 5. 编排、学习与验证

**编排选择。** 固定且可拆解的任务适合工作流；步骤必须根据观察调整时适合自主循环。比如报销材料整理可以让模型自主查找缺漏，付款动作则用确定性校验。更复杂的 Harness 不自动等于更可靠，新增节点必须解决实际出现的稳定失败。

**三类学习不要混淆。** 工具反馈写回上下文是任务内适应；把经验整理到知识文件/提示词/程序是跨任务外部产物更新；训练修改参数才是模型参数学习。本次笔记属于外部产物，未微调任何 LLM。本地 Q-learning 更新的是游戏策略的 Q 表，不代表训练了语言模型。

**消融的变量必须精确。** `no_tool_calls` 在当前实现中实际移除工具定义；`no_reasoning` 去掉写回历史的 reasoning 字段，不是关闭模型内部推理。隐藏工具结果时，空字符串和“结果被隐藏”的提示并不等价，后者多给了一个可感知信号。当前书稿/实验 README 已指出 `no_reasoning` 的退化未在其所述真实运行中复现；离线测试不能推导模型效果。

**可迁移的原则。** 审核看证据而非产出者的自我解释；先给目录再按需读细节；追加轨迹便于复核；修改同时检查目标样本和保留样本；每次修改尽量小且可回滚。原则能保留，实现方式要随着实验结果更新。

## 6. 思考题自答

- **只能加强一个组件？** 先用轨迹找瓶颈。看不到数据就补上下文，不能执行就补工具，有数据有接口仍判断错才升级模型。增加无关上下文/工具反而可能增加选择成本。
- **怎样防止循环失控？** 同时记录重复动作及其参数、连续失败、状态是否有进展；限制轮数/时间/成本；达到阈值保存部分成果与失败原因，停止副作用并移交控制。
- **模型越强，为何还需 Harness？** 决策能更自主，能触达的环境也更广；身份权限、真实执行、证据和恢复仍需要工程保障。
- **缓存为何可能近似二次增长？** 若每轮新增固定长度消息，第 k 轮读取的历史近似与 k 成正比，总读取量是等差数列之和。前缀缓存降低重复计算，却不直接消除逻辑读取量；摘要、分层检索和更少无效轮次可减少历史负担，要验证不丢关键证据。
- **用户暂时不在线怎么办？** 保留上下文、已完成步骤和待解决问题；只推进已有授权范围内独立且可逆的工作。不能把等待超时当成新的授权。
