# 整章串讲 从回答问题到持续交互

[学习导读](index.md) · [客服项目](events.md) · [3D 课堂](voice.md)

## 1 为什么前五章的循环还不够

前面的简化循环是：用户给任务，模型想一想，调用工具，看到结果，再回答。这个模型方便理解，但默认了一个条件：**在这一轮结束以前，外部世界可以等。**

现实中的家长可能在查课表时补充“不是大宝，是二宝”；学生可能在老师念例句时说“我还没听清”。旧任务还没结束，新信息已经让旧计划不再适用。

因此第六章增加了两根轴：

|轴|问什么|客服项目例子|课堂项目例子|
|---|---|---|---|
|模态|输入和输出是什么形式？|文本、图片、消息卡片|学生 PCM 音频、转写、老师语音、页面动作|
|时机|信息什么时候可以进来，动作何时应停止？|工作流执行中改口、回执迟到|老师播放中插话、旧音频迟到|

**模态变多不自动解决时序问题。** 给模型加一个音频输入接口，并不能自动清掉前端缓冲的旧声音。

## 2 事件到底是什么

事件是“某件事发生了”的记录。例如，用户说了一句话、查询完成、定时器到期、老师音频已经播完。

下面是教学设计，不是课程或公司统一协议：

```python
# 教学简化：用字典表示一条事件
incoming = {
    "event_id": "evt-17",       # 同一事件重发时用它去重
    "session_id": "chat-demo", # 路由到哪一个会话
    "kind": "user.message",   # 谁产生的哪类事实
    "revision": 3,              # 发生时属于哪个任务版本
    "payload": {"text": "改成周六"},
}
```

`event_id` 回答“是不是重复送来”，`session_id` 回答“送给谁”，`revision` 回答“它属于哪一版任务”。这三个 ID 不能互相替代。

`payload` 是事件具体内容。若来源是外部工具，它仍是工具提供的数据，不会因为被塞进消息列表就自动变成有权改变系统规则的指令。

## 3 新事件来了 有三种不同处理

### 3.1 补充条件 可以等到安全点

家长：“查一下课程。”查询期间补充：“只看周末。”

先保存补充条件，等适合更新上下文的边界一起处理。“安全点”是可以安全整理状态并作下一步决策的位置，不一定是操作系统线程切换点。

风险在于模型只记住最后一条消息。因此状态不能只有 `last_message`，还要保留所有尚未处理的约束。

### 3.2 取消旧计划 必须改变执行状态

家长：“别查这个孩子了，我说的是另一个孩子。”

这里不仅要接收文字，还要取消或作废原任务，避免旧孩子的查询结果变成新问题的回答。`cancel()` 尽量停止计算；版本检查决定结果还能不能产生副作用。它们解决不同问题。

已经发送的微信消息、已经播放的声音，不会因为取消而从用户记忆里消失。必要时应明确纠正，不能把取消描述成回滚一切。

### 3.3 独立问题 可以单独推进

慢查询进行中，用户问一个不依赖该查询的小问题，可以用独立工作处理。是否真的“立即”回应，取决于执行架构是否有独立通道。

**课程正文的并行推理设计，与 6-2 简化 runtime 不完全相同。** 该 runtime 的 `IMMEDIATE` 事件进入 `work` 队列，仍由单个 `_worker` 顺序处理；它可以不等后台工具，但若前一个 LLM turn 尚未结束，仍可能等待。不要把枚举名 IMMEDIATE 当作零等待保证。

## 4 Python 异步 模型异步 与用户引导不是一回事

|层次|实际承诺|没有承诺|
|---|---|---|
|Python `asyncio`|当前协程等待可挂起，让别的任务运行|不会自动让两行顺序 `await` 并行，也不改变模型协议|
|启动任务并返回句柄|调用返回 `task_id`，工作继续在后台跑|返回句柄不是业务完成，不能编造结果|
|模型原生异步工具|工具结果未到时，模型可继续不依赖结果的工作|供应商不会替应用管理所有后台任务|
|Mid-turn steering|运行中接入新用户要求|不撤销已执行操作，也不自动取消已启动工具|

官方异步工具文档把工具执行责任留给应用；steering 文档也明确区分“已接收更新”和“已按更新行动”。本次只学习协议，尚未运行原生能力实验。[异步工具调用](https://developers.openai.com/api/docs/guides/async-tool-calling) · [运行中引导](https://developers.openai.com/api/docs/guides/steering)

### 一个你能自己解释的例子

```python
# 教学简化：先等查课表结束，再查订单，是顺序执行
calendar = await lookup_calendar()
order = await lookup_order()
```

```python
# 教学简化：两个查询不互相依赖，才可以并发等待
calendar, order = await asyncio.gather(
    lookup_calendar(), lookup_order()
)
```

第二种的等待可能接近较慢的查询，而非两者之和。但如果订单决定应查询哪个孩子的日历，就存在依赖，不能直接这样改。接口限流、资源竞争也可能抵消并发收益。

## 5 语音让同样的问题变得更紧迫

客服晚一点发送可能只是显得慢；课堂在学生说“等等”后继续讲，会直接盖住学生的声音。三段式的每个阶段都可能形成积压：

```text
音频输入 → ASR 临时/最终文本 → LLM 增量文字
                               ↓
                         TTS 音频块 → 播放队列 → 实际听到
```

一边输入、一边生成和播放，需要应用层并发处理。原生全双工模型进一步把持续听说的决策纳入模型。两者有关联，但不能因为链路用了多个模型，就断言系统一定只能严格轮流说话。

详见 [课堂语音节奏](voice.md)，其中会区分 VAD、语义轮次、ASR final、流式生成和播放回报。

## 6 Computer Use 为什么仍是同一章

GUI 操作的循环是：观察页面 → 决定动作 → 执行 → 再观察。关键不是模型“说要点哪里”，而是执行后目标页面是否真的出现。

当页面有结构化元素时，可以把动作指向元素 ID；只有截图时，需要视觉定位和坐标映射。无论采用哪种定位，页面都可能在模型思考时改变，因此不能无限重放旧计划。

对当前两个项目的启发是：**有明确业务接口时先利用接口和回执，不必为了使用 Agent 把可靠 API 换成鼠标点击。** 3D 老师的课件动作也需要执行回报；发送了翻页标签，不等于页面已经完成切换。这是设计类比，不是声称课堂项目采用 Computer Use。

## 7 机器人部分要记住的结构

这一节先学控制分层，不急着学习所有模型名字。

|层次|负责什么|不该混淆的东西|
|---|---|---|
|规划|先移动杯子还是先清理纸张|任务规划不是关节控制|
|受限技能|抓、放、观察、停止|工具名表示期望动作，不表示一定成功|
|动作策略与底层控制|生成并执行局部运动|模型推理频率不等于执行器控制频率|
|世界模型|预测某个动作可能产生什么后果|预测不能替代真实观察|
|验收|实际物体是否在目标位置|模拟成功不证明真机成功|

动作分块可减少等待，但块越长，按照旧观察继续执行的时间也越长。语音里同样存在类似取舍：预先缓存较多音频能平滑播放，却增加停播时需要清理的积压。它们是相似的工程问题，不是同一个控制算法。

## 8 整章最值得带回工作的结论

把“生成了什么”与“现实发生了什么”分开记录。前者是候选，后者是证据。

- 客服：草稿生成、发送请求成功、渠道回执，是不同状态。
- 课堂：文字生成、TTS 合成、媒体交付、实际播放，是不同状态。
- GUI：动作提出、点击执行、目标页面出现，是不同状态。
- 机器人：计划生成、轨迹下发、物体归位，是不同状态。

读完这一章，应能说清：**谁提供观察，谁决定下一步，谁执行，谁确认结果；新事件到来时，哪份旧工作必须停止或失效。**

??? question "自测：用户改口后，旧查询返回了正确数据，要不要发送？"

    不能只看数据是否正确，还要看它是否属于当前有效问题。旧查询对旧问题可能正确，对新问题却可能无关甚至误导。应核对任务 ID、会话归属和当前版本；已经发生的业务动作另查回执，不应凭过期版本一律假装没发生。
