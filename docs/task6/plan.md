## 1 每一课如何上

1. **给出一个具体失败场景。** 例如“家长补充了孩子身份，旧回复还是发出去了”。
2. **先画状态和数据流。** 标出队列、任务、消息、结果和交付边界。
3. **只读三个以内的关键函数。** 找入口、状态变化和退出条件，不从大文件第一行一路读到底。
4. **做一组最小对照。** 每次只改一个机制，提前写预期，不看到结果再改判分规则。
5. **一起读日志。** 不只看最后 PASS，要能指着某条事件解释发生了什么。
6. **自己改一个条件。** 先预测后运行；能够解释新结果，才继续下一课。

每课笔记包含：SVG、教学简化代码、真实源码定位、输入、完整时序、通过/失败证据和未覆盖边界。新课不覆盖旧证据。

### A1 的第一节先做什么

**场景：** 用三个合成事件模拟家长“查课程”“补充只看周末”以及一条后台查询完成通知。先看它们如何进入队列和被处理，不发真实微信、不使用真实客户数据。

第一遍沿用课程 `event_loop_demo.py` 的事件入队/分发方式；处理器先是确定性本地函数，发送器仅记录到内存或文件。这个版本验证的是事件机制，不验证模型意图识别。

第二遍在相同事件协议下再接模型，检查它是否理解内容。这个阶段再新增请求、响应与成本证据，不能把第一遍的成功冒充模型成功。

**读代码顺序：** `Event` → `TriggerSource.emit` → `EventLoop.run` → `dispatch`。最后才进入 `EventTriggeredAgent.handle_event`，此前不读全部 MCP 和 provider 代码。

预先写下四个检查：

- 事件到达后是否触发处理，而非等一个新用户请求才处理？
- 连续事件顺序能否从记录中还原？
- 一个处理器失败后，下一条是否仍可处理？
- “本地记录交付成功”是否与真实渠道送达明确分开？

**第一遍不声称已完成去重或抢占。** 课程最小 FIFO 循环没有因为存在 event_id 就自动获得幂等。重复投递、跨会话隔离和过期结果作为后续扩展，避免一上来把十种机制混在一起。

### A2 学什么新代码

读 `runtime.py::_dispatcher / _worker / _handle_interrupt`，再读 `tasks.py::cancel / _terminate_process`。前半部分决定事件怎么走，后半部分确认任务是否真的停。

重点区分：

```text
已提出取消 → 任务收到取消 → 执行器停止 → 旧结果不能交付
```

不能只看到日志里打印“已取消”就宣布成功。课堂的停播也会复用这个思考方式，但这一课先使用客服任务场景。

### A3 何时值得调用原生 API

先学懂普通运行时版本，再做原生能力对照。否则 API 多了几个事件，看不出它替应用省掉了什么、仍留下了什么。

为避免把协议差异和模型能力混在一起，运行时要保存模型名、请求参数、实际响应、事件序列。暂时只有兼容模型凭据时，可先读源码和录制事件结构，原生运行保持未执行，不能伪装成同一实验。

### B1 为什么先测真实链路

模拟 `sleep(0.3)` 可以解释时序，却不能回答线上 ASR、LLM、TTS 或网络谁最慢。第一课可以先画模拟时间线，但一旦写“实测响应延迟”，就必须有真实音频输入与真实阶段时间戳。

优先使用合成或明确授权的测试语音，逐一说明是否真实模型、真实传输、真实播放。文字回放不能当作声学 VAD 评测；拿到音频文件也不等于验证了实时听感。

### B2 先固定这些边界场景

- 老师还没出声，学生就补充一句。
- 已生成整句话，但只播放了前半句。
- 打断清理中旧 TTS 又到达一个包。
- 旧打断判定返回时，新 generation 已开始。
- 学生只附和“嗯”，以及明确要求“老师等等”。

前四类先验证确定性时序；最后一类涉及语义策略，需要单独数据和误判统计。不要混成一项“打断成功率”。

当前先保留概念阅读，不进入执行计划。6-8～6-9 对理解课件动作后的状态校验有启发；6-10～6-14 对控制分层和观察过时有启发。它们不是当前提升客服或课堂节奏的第一优先级。

## 5 学完一课 你应该能独立讲出来

不用背函数名，能回答五个问题即可：

1. 输入是什么数据结构，谁创建？
2. 当前状态放在哪里，谁能修改？
3. 哪一步在等待，等待时别人还能做什么？
4. 出错或改口后，哪些结果作废，哪些事实不能撤销？
5. 什么证据说明任务完成，而不仅是程序执行结束？
