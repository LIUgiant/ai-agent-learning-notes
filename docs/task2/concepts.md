# 第 2 章概念 · 上下文工程在管什么？

五个实验看起来各做各的：缓存、提示词、注入、状态栏、压缩。它们其实在回答**同一组问题**——模型每次请求看到的上下文，该放什么、怎么放、放多久。

## 上下文的三个问题 → 五个实验

| 问题 | 实验答案 |
| --- | --- |
| **放什么**（哪些信息值得进上下文） | 2-4 提示词消融：语气/组织/工具描述的边际价值；2-5 注入防御：哪些通道的内容**不配**被当指令 |
| **怎么放**（组织方式的经济性） | 2-3 KV Cache：同样的内容，追加式构造让前缀缓存命中、重建式构造全量重算；2-9 状态栏：动态信息放末尾（不毁前缀）且教模型怎么用 |
| **放多久**（历史的信息生命周期） | 2-10 压缩：立即摘要换瘦身 vs 原文进历史、满了再老化压缩 |

## 五个核心概念

| 概念 | 一句话 | 实验锚点 |
| --- | --- | --- |
| KV Cache / 前缀缓存 | 服务端把上次请求算过的注意力键值存下来，下次请求**从头逐 token 相同**的部分直接复用；失效从第一个差异点开始，之后的全部作废 | [2-3](kv-cache.md)：dynamic_system 命中 0% |
| 提示工程三要素 | 语气风格、信息组织、工具描述——对强模型的边际影响可能有限，但要靠客观基准说话 | [2-4](prompt-engineering.md)：六臂消融 |
| 注入通道 | 用户消息、工具返回的数据、持久记忆——三处都不是"本人写的指令"；防御分表示层（说服模型）与执行层（不信任模型） | [2-5](prompt-injection.md)：3×4 战役 |
| 状态栏（system hint） | 时间戳/工具计数/TODO/详细错误/系统状态，插在**每轮末尾**的临时消息——动态内容放尾部不毁前缀缓存 | [2-9](system-hint.md)：combined 3/3 vs 0/3 |
| 压缩时机 | 立即压缩（工具返回时摘要，历史永久瘦身）vs 老化压缩（原文保真，超阈值批量摘要旧的） | [2-10](context-compression.md)：no_compression 溢出死亡 |

## 把它们串成一条线

一次 Agent 请求的上下文 = `tools 定义 + system + （历史消息…）+ 本轮新内容`：

```text
[tools][system] ←—— 2-4：这两个的写法值多少分？
                ←—— 2-5：system 里的机密、tools 返回的数据，谁在试图越权？
[历史…]        ←—— 2-3：这段前缀逐字节稳定吗？缓存能不能用？
                ←—— 2-9：要不要在末尾临时垫一条状态栏？
                ←—— 2-10：历史太长了，压掉还是等爆窗？
```

缓存实验（2-3）是其余四个的"经济学基础"：2-4 的语气块放在 wiki 前面反而是缓存友好的（固定文本）；2-9 的状态栏每轮都变、但放在末尾所以不付缓存代价；2-10 的 windowed 压缩改写历史会破坏前缀（被压缩的消息变了）——压缩省 token 的同时可能毁缓存，这笔账课程没算，是真实系统要权衡的。

## 对自己的项目有什么用？

**老师（客服）项目**：

- 工单上下文按"稳定→易变"排序：业务规则、工具定义放前面且**冻结**（别塞时间戳/随机数），工单状态、最近工具结果放后面——直接套 2-3 的 correct 模式；
- 客服知识库的检索结果进历史前先摘要（2-10 的 context_aware：按当前工单问题聚焦），带引用的版本还方便审计答案出处；
- 读取用户上传的网页/文档时按 2-5 的 D3 打来源标记——外部内容是数据不是指令，高风险操作（退款、改订单）走 D4 式运行时授权。

**实时对话项目**：

- 多轮对话的状态栏（2-9）：每轮末尾垫"当前时间/已尝试的工具/待办"比把它们写进 system 更省缓存也更醒目；
- 对话历史的压缩分龄处理：最近 N 轮原文保真（实时对话需要细节），更早的轮次老化摘要（2-10 windowed 思路）；
- 注入风险点在实时对话里更突出：用户消息本身就是攻击面（2-5 直接注入通道），外链预览/表情包 OCR 结果是间接通道。

具体字段要回到两个项目的代码再确认，这里只建立对应关系。
