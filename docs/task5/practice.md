# 项目结合 · 从学习机制到自己的实现

本页围绕你提到的老师/客服和实时对话项目提出设计方向。没有检查这两个项目当前代码，所以不声称它们已经有下面的缺陷或能力。

## 一、老师/客服：把解释、判断、执行分开

假设一个业务动作需要资格判断，建议先画出三步：

1. **查询事实**：订单/课程/权益当前状态，返回来源与更新时间。
2. **计算资格**：后端返回 eligible、reason_code、允许的下一步。
3. **提交操作**：再次检查当前状态与权限，再执行；返回 operation_id 和结果。

模型承担解释、追问、选择下一步；前后端共享明确的资格口径。不能把模型 `expected=True` 当成授权。

### 为什么查过一次仍要提交时再检查

查询与执行之间可能发生状态变化：另一个请求已取消、权益已被使用、库存发生变化。查询给模型理解事实，提交时检查保证动作基于当前状态。本次课程内存环境没有并发竞态，迁移时需另行设计事务或版本约束。

### 可以先加的三个用例

| 用例 | 预期 | 观察什么 |
| --- | --- | --- |
| 正好在允许边界 | 应办成功 | 资格函数、prompt、工具参数口径是否一致 |
| 用户声称满足，但实际不满足 | 应拒绝 | 后端状态有没有变化，回复是否误承诺 |
| 后端允许，模型却直接拒绝 | 应被评测发现 | 不只统计拦截，还要统计漏办 |

“后端可以拒绝”不等于用户体验好。失败后模型应解释原因、提供真实允许的替代动作，而不是换句话重复承诺。

## 二、实时对话：把生成状态与业务状态分开

建议画出两张状态表：

| 对话生成状态 | 可能变化 |
| --- | --- |
| 当前 turn_id | 新用户输入后递增 |
| 文本缓冲 | 接收中 / 完整 / 已废弃 |
| 音频播放 | 排队 / 播放 / 已停止 |

| 业务操作状态 | 可能变化 |
| --- | --- |
| operation_id | 用于去重与查询 |
| 操作 | 未提交 / 已提交 / 成功 / 失败 / 结果未知 |

用户说“等等”后，旧音频应停止，但已经提交的操作不能通过清空音频队列来撤销。请求超时也不等于操作失败：可能服务端已成功但回执没到，需要先查状态。

**学习版伪代码，未集成你的项目：**

```python
turn_id = session.start_turn()
for chunk in generate_text():
    if turn_id != session.current_turn_id:
        break
    session.append_text(turn_id, chunk)
# 有副作用操作的完成/查询，必须另走业务 operation_id
```

只在接收文字时检查还不够，TTS 合成回调、播放队列消费也应检查旧 turn 是否已失效。这是从文字流实验迁移的设计练习，不是本次已经完成的音频实现。

## 三、两个项目都能受益：固定日志与验收

先选一个真实但脱敏的失败案例，记录：request_id、turn_id、tool_call_id、operation_id（如有）、输入摘要、返回状态、错误码、耗时、版本。不要为了调试把密钥或敏感原文直接写入日志。

然后写三条可执行检查：

- 操作成功声明必须有对应成功回执。
- 业务前置检查发生在操作之前，且作用于同一个对象。
- 失效 turn 的输出不会进入当前展示/播放通道。

为每条检查构造一个应该失败的例子。若错误例子仍通过，说明验证器本身不够强。

## 四、自己写代码的路线

### 第一步：纯 Python，先不用 API

运行 [offline_walkthrough.py](../assets/task5/offline_walkthrough.py)，也可复制到 Python Tutor。看 messages 从 1 条增长为 3 条，看 JSON 字符串怎样变回 dict，看存在性检查为何漏掉顺序错误。

### 第二步：把假响应替换成一次真实模型调用

保留同样的数据形状，先只暴露一个只读工具。检查 tool_call_id 是否正确连接，返回错误是否真的进入下一轮。

### 第三步：增加状态变更与验收

加入一个可逆的教学动作，执行前校验、执行后读状态。不要一开始就接真实业务写入。使用 fixed tests，避免模型为了“绿灯”修改验收条件。

### 第四步：刻意制造失败

改变边界条件、截断参数、移除前置步骤。观察模型反应之外，还要观察后端状态、测试结果和重复调用。

### 第五步：再接你的具体项目

把课程夹具替换成业务适配器，保持模型、工具、状态、验证四层职责不变。优先迁移日志与验收，再扩大自动执行范围。

## 五、学完后应能独立回答

1. SDK message 和发给 API 的消息字典如何互相转换？
2. 工具参数为什么先是字符串，何时才能执行？
3. 当模型不调用工具时，后端守卫为什么帮不上忙？
4. 重发当前轮会保留什么，丢掉什么？
5. 工具 fingerprint 与业务幂等键有什么区别？
6. 测试在修复后通过，为什么还不够？
7. step_present 与“必须先执行”相差哪个判断？
8. 用户打断后，停止输出与撤销操作为什么是两回事？

能用本次一条真实轨迹解释这些问题，比把整个目录从头读到尾更接近掌握源码。
