# 知识点地图 · 从模型回答到程序验收

> 先读 [正文串讲与架构选择](reading.md)，把本页的数据结构和机制放回整章的问题中。

## 1. Coding Agent 多出来的，不只是“会写代码”

普通对话常在回答文本后结束。Coding Agent 需要把输出落实到文件与运行结果：发现文件、理解现状、提出修改、应用修改、执行测试、根据结果继续。**代码是它能操作的一种工件，执行循环才是核心。**

| 层 | 负责什么 | 这次看到的具体数据 |
| --- | --- | --- |
| 模型 | 提出下一步操作或最终答复 | `assistant.tool_calls`、最终文字 |
| 运行框架（Harness） | 维护历史、调度工具、限制轮数、传回错误 | `CodingAgent.run()`、`MAX_TURNS` |
| 工具 | 执行确定动作 | 读取文件、替换字符串、计算是否可退 |
| 环境状态 | 保存已经发生的事实 | 文件内容、`refund_issued`、HTTP 响应 |
| 验证器 | 判断任务是否满足要求 | unittest 退出码、状态评分、回归断言 |

不要把“助手说好了”当作环境状态。模型即使输出“已退款”，如果 `refund_issued=0`，实验仍可能判失败。

## 2. Tool schema、参数和实现是三样东西

**教学示意：**

```python
schema = {"name": "Read", "parameters": {"file_path": "string"}}
arguments = {"file_path": "/workspace/policy.py"}
result = read_file(arguments["file_path"])
```

schema 告诉模型“能做什么、要给什么参数”；arguments 是本次调用的输入；read_file 是真正运行的 Python。schema 写了 required 不代表所有本地入口都会自动验证它。先检查调用框架有没有做校验，不能把接口描述当作权限机制。

## 3. message 与 messages 分别是什么

- `messages` 是 Python `list`，按顺序容纳多条消息。
- 单条发送消息通常是 `dict`，有 `role`、`content` 等字段。
- SDK 返回的 `response.choices[0].message` 是 SDK 对象，属性读取与字典索引不是一回事。
- `tool_calls` 是调用列表；其中 `function.arguments` 常常是 **JSON 字符串**，不是已解析的 dict。

```python
# 教学示意：三次取值，类型分别是 list → dict → str
messages = [{"role": "tool", "content": '{"refund_amount": 505}'}]
message = messages[0]
text = message["content"]
# json.loads(text) 才得到可以访问 refund_amount 的 dict
```

工具结果常经历 `dict → json.dumps → content 字符串 → API`。本地变量结构与网络协议格式必须分开理解。

## 4. 代码守卫是什么，能保证到哪里

守卫是在状态变更前执行的检查，例如 `actual_refundable` 为假就拒绝退款。它能阻止**到达这个入口的错误操作**，但不能让一个已经放弃的模型主动调用正确操作。

本次 exact-24h 误拒就是后一种：规则代码是对的，模型却没调用。工程上应分别统计误执行、漏执行、错误承诺，不能只统计“拦截了多少次”。

另外，课程两臂同时改变 system prompt、schema 描述/checklist 与后端校验。它是一个**组合方案对照**。若要归因，应增加“同 prompt + 同 schema，仅切换后端守卫”的第三组，而不是把所有差异都归因于代码。

## 5. 流式输出是一连串增量

`delta` 表示这次新增的片段，不是完整答案。

```python
# 教学示意，适合放进 Python Tutor
parts = ['{"ci', 'ty": "', '东京"}']
buffer = ""
for part in parts:
    buffer += part
# 最后 buffer 才是完整的 JSON 文本
```

本轮有多个工具调用时，还要按 `index` 分开缓冲，否则两个 JSON 会串在一起。流结束后也不只检查能否解析：需要检查必需字段、值是否正确、调用是否仍属于当前任务。

## 6. 重试、续写、接管、用户打断不是同一个问题

| 名称 | 什么发生了 | 本次范围 |
| --- | --- | --- |
| 整轮重发 | 丢掉当前轮半截，保留已提交历史重新请求 | 已跑 |
| 元指令恢复 | 把断点描述给模型，要求继续 | 已跑 |
| 原生前缀续写 | 使用厂商特定机制让模型接在指定前缀后 | 未跑 |
| 跨厂商接管 | 把轨迹转换为另一个模型可接受的格式 | 只读相关代码，未跑 |
| 用户打断 | 新意图使旧回复或旧操作失效 | 仅给迁移设计，没有音频实测 |

重复调用检测也不等于幂等性。幂等性要求同一业务操作重复请求仍只生效一次，需要服务端操作标识、原子记录与结果复用。本次机票工具是只读函数，检测到的“重复副作用”字段实质是重复调用提议，不是真实扣款次数。

## 7. 日志诊断需要三个输入

**日志告诉你发生什么，架构告诉你组件如何连接，PRD 告诉你应该怎样。** 没有 PRD，看见“退款前没校验”也无法确定它是不是 bug；没有日志，PRD 再完整也不能证明某次执行违规。

模型生成测试后，程序必须能解释这个测试。课程用固定断言类型（小型 DSL），由 `_evaluate` 分发执行，避免把自然语言“应该没有问题”当成检查结果。

## 8. 三类验收不要混淆

1. **结构有效**：JSON 能解析、字段齐全、引用的轨迹存在。
2. **语义正确**：城市是东京、24 小时含边界、先验资格后退款。
3. **结果可证**：操作实际生效、错误版本失败、正确版本通过。

三个实验反复训练的都是这件事：把每个成功结论对应到一个真正检查过的对象。
