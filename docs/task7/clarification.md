# 9-4 实验：什么时候直接做，什么时候先确认

[一步步读代码](clarification-code.md) · [运行证据与源码包](evidence.md)

!!! note "实现来源和实验边界"
    课程只有正文实验要求，仓库没有 9-4 配套实现。本次是依照正文编写的**教学实现**：DeepSeek 真实调用；任务、用户回答与反馈是我们预先设计的模拟数据；交付物是结构化配置方案，不是真实应用代码或线上变更。它验证沟通协议与门禁，不能证明真实用户满意度。

## 1 要解决的是两种相反的失败

- “给企业客户加登录”：不问身份提供商、旧登录兼容和上线范围，容易自作主张。
- “把按钮提交改成发送”：需求已经明确，还反复确认，会打断工作。

所以我们比较三条完整策略：

|策略|步骤|潜在代价|
|---|---|---|
|direct|直接生成配置|隐含需求可能猜错；高风险无确认会被拦|
|ask|提问 → 模拟用户回答 → 生成配置|知道答案，但没有批准具体版本|
|spec|提问 → Spec → 模拟用户确认 → 生成配置|更可控，也增加交互|

“问过问题”不等于“用户批准了这一版高风险变更”。

## 2 数据怎么分，避免偷看答案

第一轮 6 个任务：训练 T1 按钮、T2 企业登录、T3 聊天记录清理；留出 H1 页脚错字、H2 助教权限、H3 公开接口分页。每题运行三种策略，共 18 条轨迹；之后候选再运行 3 条留出任务。

模型起初只看到任务、风险标签和配置选项，**看不到 target 答案**。提问时模拟用户只回答被问到的字段；确认 Spec 时模拟用户指出不符合预期的字段。评价程序始终持有 target。

风险标签由夹具提供，选项范围也预先限定，因此这里没有验证模型自动识别真实业务风险或发现任意隐藏需求的能力。低风险题都是清晰小改动，不能泛化成“所有低风险需求都无需澄清”。

## 3 第一轮三策略结果

|策略|任务数|配置偏离|合规且正确交付|门禁拦截|问题条数|低风险交互轮数|
|---|---:|---:|---:|---:|---:|---:|
|direct|6|1|2|4|0|0|
|ask|6|0|2|4|16|2|
|spec|6|0|6|0|16|4|

direct 在清理记录题猜成 30 天，预设用户需要 90 天。其他高风险题即使配置猜对，仍缺少明确确认，不能交付。ask 把字段都问对了，但也没有 Spec 确认，因此高风险任务被拦。

高风险门禁要求具体版本确认，是本实验预先设置的规则。不能把“spec 交付更多”包装成独立证明所有业务都应该强制 Spec；它首先说明实现遵守了这个实验协议。

## 4 从反馈得到什么 Skill 候选

初版：

> 所有任务都先提问，再生成 Spec，经用户确认后执行。

模型基于 T1—T3 的 9 条训练轨迹，生成一个精确替换：

> 低风险简单任务直接执行，不提问、不生成 Spec、不确认；高风险任务先提问澄清，再生成 Spec，经用户确认后执行。

来源记录为 `T1,T2,T3`。它减少简单任务的打扰，保留高风险确认。正文中的可回滚思想在这里体现为保存 old_str、new_str、来源和理由；稳定规则没有自动替换。

## 5 第一轮候选失败：文字正确，路由错误

留出任务里候选配置全部正确，但高风险 H2/H3 被选成 `ask`，没有进入 Spec，最终只能交付 **1/3**。低风险打扰减少也不能抵消这个退步，所以门禁返回 `reject_candidate`。

定位后发现：我们的初版路由请求只列 `direct/ask/spec` 名称，没有解释“完整流程”和“下一步动作”的区别。模型看到“先提问”就选了 ask。

这是**我们编写的实验接口定义不足**，不能简单归咎于 Skill。保留失败数据后，我们只补清枚举语义，没有改变 Skill 文本或放宽门禁。

## 6 修正接口，用新增任务再次检查

为避免在已看过的 H1—H3 上反复调试后声称泛化，我们增加 F1 标题修改、F2 家长回放权限、F3 录音保存策略。固定第一轮生成的 Skill，用新接口分别运行原版 spec 与候选。

|新增任务对照|spec 初版策略|冻结的候选 Skill|
|---|---:|---:|
|合规且正确交付|3/3|3/3|
|配置偏离|0/3|0/3|
|问题数|8|6|
|澄清轮数|3|2|
|确认轮数|3|2|
|低风险交互轮数|2|0|
|高风险错误|0/2|0/2|

模型按 `direct/spec/spec` 选择三题路径。程序给出 `eligible_for_simulated_canary`。这只是模拟实验的入围建议，未发布真实 Skill。

前一轮 45 次调用，新增任务 19 次，共 64 次正式模型调用。最早一次默认 thinking 导致长度截断的试跑单独保留，不混入正式结果。

## 7 哪些指标测到了，哪些没有

- **需求偏差**：最终配置是否存在不符合预设 target 的字段。
- **返工代理量**：不匹配字段数；不是实际工程返工次数或耗时。
- **打扰代理量**：提问和确认轮数；不是实际烦躁程度。
- **Spec 修改率**：第一轮 0/6，新增对照初版 0/3、候选 0/2；本轮没有观察到真实模型生成的 Spec 需要修订，不能声称减少 Spec 返工已被证实。
- **高风险错误**：门禁允许且配置错误；同时报告拦截和交付率，防止“全部拒绝”被算成成功。
- **计时**：只记录从模型流程开始到配置生成的耗时；没有真人等待时间，不代表产品端到端延迟。
- **用户放弃率、首次有效产出时间**：未测量，JSON 为 null，没有用 0 伪装。

## 8 和客服、3D AI 老师的关系

客服可以学会何时追问订单信息、何时给出方案；但不能通过 Skill 修改退款权限。3D AI 老师可以学习何时追问学生、何时直接解释；但课堂录音保留、家长访问范围等高风险变更仍需要受保护的确认流程。

本实验的确认不是要求日常讲题每句都停下来审批。它针对的是高风险配置变更，不能直接移植成实时语音对话节奏。
