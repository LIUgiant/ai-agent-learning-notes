## 为什么先做 10-4，而不是 10-1

编号不是学习顺序。10-4 有一个容易追踪的目标：几个 worker 去不同网页找同一位教师。每个 worker 的输入、结果和生命周期都能画清楚。掌握这个例子后，再比较“一条历史中切角色”和“多个私有上下文”的差异。

## 先建立四条不变量

1. **消息有信封**：知道谁发给谁、是什么类型、负载是什么。
2. **任务有生命周期**：提交、运行、完成/失败/终止，并最终释放资源。
3. **结果先验证后结算**：模型声称找到，不能直接触发全局成功。
4. **首个有效结果只能结算一次**：其他 worker 需要收到取消、应答，并真正清理资源。

本轮最有价值的反例是：网页上姓名相同、引文也真实，仍可能不是要找的那个人。因此“验证成功”必须对应明确任务条件。

## 本轮实现边界

课程原版 10-4 使用 Playwright 独立浏览器 context。我们这次把采集层替换成 HTTP HTML 文本适配器，保留原版 `WorkerAgent`、`Coordinator`、`MessageBus` 和串行调度函数，同时加入独立的姓名/身份/领域/原文引用检查。

这是用于理解协调机制的小实验，**不算原版浏览器隔离、JS 渲染与全量站点的正式验收**。HTTP 采集的真实负结果也保留：HAI 页面返回的静态文本只有标题。
