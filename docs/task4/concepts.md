# 概念：从"能力怎么表达"到"一次看见多少"

第 4 章有六个实验，但它们其实只在回答四个问题。先把这张地图立起来，后面每页都能挂上去。

## 一、能力做成什么形态：专用工具、通用执行器、Skill

同一件事（比如"部署应用"）可以做成一个 `deploy_app` 专用工具、拆成三个细工具，或者干脆不写工具、
只写一份 Skill 文档让 Agent 用终端分步执行。书里的默认取向是**往通用一端靠**：与其提供四则运算计算器，
不如给一个沙盒里的 `code_interpreter`——LLM 会写代码，给元能力比给几十个专用工具更划算。

只有四种情况值得退回专用工具：需要精细授权与审计留痕、参数结构复杂（嵌套对象/多字段联合校验）、
使用频率极高、需要屏蔽平台差异。

> 判断标准是**功能相似性和使用场景的重叠度**。文档抽取工具从 `extract_pdf_text` + `extract_docx_content`
> + `extract_pptx_content` 合并成一个 `read_document(file_type)`，降低的是模型的选择负担——它只需要记住
> "读文档就找 read_document"。

## 二、工具怎么描述：什么时候用 > 能做什么

- 描述的核心是**调用时机**，"需要获取实时信息或查找未知事实时使用"远好于"搜索相关内容"；
- **边界比能力更重要**：文件搜索工具必须写明"只能按文件名匹配，不搜内容"，因为多数调用失败的根因是
  模型不知道工具**不能**做什么；
- 参数用具体例子代替抽象规范（`timestamp`：RFC3339，例如 `2024-03-15T14:30:00Z`）；
- 附 1–5 个真实调用示例，比只给 JSON Schema 有效得多；
- 调试原则：Agent 频繁选错工具时，**先查描述，而不是先换更大的模型**。

## 三、参数怎么传：保真性

比功能缺失更隐蔽的反模式是**静默输入转换**：工具悄悄"修正"模型的参数（把中文弯引号换成直引号、
给 `git commit` 附加参数），于是模型看到的和工具执行的不是同一个世界，而它无法自行诊断。
原则：**模型感知的世界与工具操作的世界之间不能有系统性偏差**；要规范化就必须在描述和返回值里写明。

## 四、一次看见多少：三层递减的方案

工具数量上百之后，"选哪个工具"本身就是个要设计的问题。书里给了从重到轻的三层：

| 层次 | 做法 | 谁承担成本 |
| --- | --- | --- |
| 层次化组织 + 按需加载 | 系统提示词里说明分类结构，只暴露索引 | 需要维护目录 |
| 检索式预筛选 | 按语义相似度先筛一批候选再注入 | 需要嵌入索引（一次性匹配） |
| 主动工具发现（MCP-Zero 式） | Agent 在过程中声明能力缺口，系统动态检索注入，schema 追加到轨迹原位置 | 需要嵌入索引 + 处理 KV Cache + 弱模型需专门训练 |
| Skills | 只常驻 `name`/`description` 目录，用到才读正文 | 对模型能力要求更高（命令行转义） |

主动发现有一个容易忽略的工程代价：**动态注入会破坏 KV Cache**——如果把新工具定义插进静态前缀，
每加载一次就整段失效。正确做法是把新 schema 追加到上下文**末尾**并固定在原位置，作为普通历史消息
继续命中缓存；状态栏只维护一份简短的工具名列表。

## 五、本任务六个实验分别卡在这张图的哪里

| 实验 | 变量 | 在问什么 |
| --- | --- | --- |
| 4-1 主动工具发现 | 全量 127 schema 注入 vs 三工具 + 按需注入 | 第四问：披露策略换了，强模型还差多少 |
| 4-2 感知工具 MCP | 真 MCP 服务器 127 工具、28 案例 | 第三问的落地：工具描述、参数、返回值与安全边界的完整形态 |
| 4-3 多模态三范式 | 原生 / 提取为文本 / 工具化 | 第一问：多模态能力该做成"模型原生"还是"一个工具" |
| 4-4 执行工具安全门 | 15 条门禁 | 执行工具特有的问题：**错误的代价** |
| 4-5 协作工具 | 子 Agent + HITL + 通知 | 能力超出单 Agent 边界时，把子任务交出去 |
| 工具选型 | 全量 / 检索 / 主动发现 | 第四问的定量版：recall、token、命中金标 |

## 六、贯穿全部工具的一条主线：ACI

书里把上面四条原则统称 **ACI**（Agent-Computer Interface，对标 HCI）：工具应对应 Agent 的**目标**，
而不是底层的 API 操作。这条主线在 4-4 里最尖锐——执行工具的错误不可逆，所以要在"能力开放"和
"安全约束"之间做**多层**防护：输入验证 → 权限控制 → 提议者-审核者（事前审批/事后验证）→
Sidecar（与主思考并行、门控单次调用、只读结构化字段以防话术注入），再加上幂等性与"预检-确认"两段式。

一个具体结论值得单独记：**提议者-审核者要求两个模型能力相近但家族不同**（认知多样性），
而 **Sidecar 可以用轻量模型**——因为它审查的是"这条命令是否危险"这样的分类问题，不是开放式思考。
